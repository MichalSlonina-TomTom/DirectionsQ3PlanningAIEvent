# Picking a good feature to build with Claude

This report is about the **Pick** step alone — choosing *which* feature to build with Claude before any planning or coding starts. (The full Explore → Plan → Build → Verify → Share loop is covered in the companion report; this one stops at selection.) For a conference-talk demo the stakes are doubled: you need a feature Claude can drive to a clean, visible finish on stage *and* one rich enough to showcase real technique. The selection criteria below are the filters that find that feature.

The throughline across every source: a great demo feature is one Claude can drive **with occasional oversight** — it can verify its own work, its scope is bounded and off the critical path — while still being big enough to demonstrate multiple techniques. Poorly-suited features are the inverse: unverifiable, architecturally load-bearing, ambiguous, or touching shared/production infrastructure where an overeager agent can do real damage.

A cross-cutting heuristic from Anthropic's *Building Effective Agents* frames the whole decision: don't reach for an agent unless the task warrants it — "agentic systems often trade latency and cost for better task performance," and for many jobs a single well-prompted call is enough. Agents are justified where there is genuine open-endedness *plus* clear success criteria and feedback loops, in a trusted/sandboxed environment with human oversight. The ideal demo feature sits exactly in that sweet spot ([building effective agents](https://www.anthropic.com/research/building-effective-agents)).

## Valuable

Lean toward task categories where agents demonstrably pay off, so the demo lands as obviously useful rather than as a toy. Practitioners point to boilerplate/routine code, generating comprehensive test suites, documentation, mechanical refactors and migrations, and translating standards (e.g. an OpenAPI spec into data models) into code ([beyond the vibes](https://blog.tedivm.com/guides/2026/03/beyond-the-vibes-coding-assistants-and-agents/)).

Frame the value as a **measurable constraint**, not an "AI-powered" label. Internal hackathons that underdeliver "almost always have a design problem," and broad themes like "build something with GenAI" make every team converge on the same chatbot or summarizer. Better framings state value as something you can later measure against — a problem frame ("cut support handle time by 30%"), a workflow frame, or a technology frame ([internal AI hackathon](https://angelhack.com/blog/ai-internal-hackathon/)). Pin the Must-Haves to a single measurable outcome and treat anything not serving it as a cut candidate ([MVP scoping](https://www.thinslices.com/insights/build-the-right-first-version-by-mastering-mvp-scoping)).

**Honest evidence, with its limits stated.** There is preliminary signal that the payoff is real even in brownfield: a survey of a structured Builder/Reviewer approach reported a weighted-average 26.9% productivity improvement and that 83% of participants spent less time fixing/rewriting code. The authors are explicit that these are self-reported and "should be interpreted as preliminary evidence of practitioner sentiment rather than causal effects" — treat as motivation, not proof ([arXiv 2512.01155](https://arxiv.org/abs/2512.01155)).

**Caveat — keep value high, stakes low.** The same practitioner who lists the high-value categories warns that agents have "sycophantic personalities" and will implement insecure patterns if told to, lacking independent critical judgment ([beyond the vibes](https://blog.tedivm.com/guides/2026/03/beyond-the-vibes-coding-assistants-and-agents/)). So "valuable" should not mean security-critical or architecturally load-bearing work where bad judgment is costly.

## Researchable

A researchable feature has a clear goal but enough exploration that the agent's research and planning are worth watching on stage. Anthropic frames the choice as workflows ("predictability and consistency for well-defined tasks") vs. agents ("flexibility and model-driven decision-making… at scale"), with agents fitting "open-ended problems where it's difficult or impossible to predict the required number of steps" ([building effective agents](https://www.anthropic.com/research/building-effective-agents)). For a talk you want the middle: open-ended enough to need an agent, specified enough to land. The "explore first, then plan" and "provide specific context" advice — reference specific files, point to an existing pattern like "`HotDogWidget.php` is a good example" — is what makes a researchable feature go smoothly ([best practices](https://code.claude.com/docs/en/best-practices)).

**Can you and Claude actually reach the context before time runs out?** The bottleneck is usually data access, not compute: gated internal data on day one breaks an event and teams default to useless synthetic datasets within hours. Pick a feature whose required data, APIs, and prior art are already reachable ([internal AI hackathon](https://angelhack.com/blog/ai-internal-hackathon/)). On the builder side, research the resources available at *this* event/repo first — mentorship, APIs, starter templates — and confirm an existing solution doesn't already solve it well; reuse boilerplate and SDKs rather than building from scratch ([scope a hackathon project](https://medium.com/hack-western-2015/how-to-scope-a-project-for-a-hackathon-e3b03fca4751)).

**Caveat — an unambiguous target is still required.** Independent practitioners stress that vague or evolving requirements make agents "drift," and that agents are "task orientated at the expense of the big picture" — they implement a request "quite literally and with no regard to how the rest of the system is designed" ([beyond the vibes](https://blog.tedivm.com/guides/2026/03/beyond-the-vibes-coding-assistants-and-agents/)). A useful build-time tell of over-scope or vagueness is repeated misalignment — the agent keeps missing details or implementing differently than expected, forcing multiple iterations; if you hit that in the first hour, narrow the slice mid-flight ([keep agentic AI simple](https://timdeschryver.dev/blog/keep-agentic-ai-simple-a-practical-workflow-for-software-development)).

## Parallelizable

**Treat parallelizability as a property you must prove on a whiteboard, not a default.** The headline caveat from Anthropic's own engineering team: "Most coding tasks involve fewer truly parallelizable tasks than research, and LLM agents are not yet great at coordinating and delegating to other agents in real time" ([multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)). The precise claim is that parallelizable coding subtasks are *rare* and agent-to-agent coordination is still weak — so choose a parallel-demo feature *because* it is one of the rare ones, and say so on stage. Anthropic's rule for a bad fit: "Some domains that require all agents to share the same context or involve many dependencies between agents are not a good fit for multi-agent systems today."

**The disjoint-files test is the single most predictive signal.** Good candidates: independent features (UI components, separate API endpoints, integrations that don't touch shared core logic) and refactoring separate modules. Bad candidates: shared core infrastructure (two features both editing core auth middleware will conflict) and database schema changes to shared tables ([parallel dev playbook](https://www.mindstudio.ai/blog/parallel-agentic-development-playbook)). The strongest concrete pattern is **directory-level ownership** — assign each agent a distinct folder, with sharp one-sentence scopes ("Build a `POST /api/users` endpoint that accepts `{email, password}`…", not "Build the user API") ([agent teams](https://www.mindstudio.ai/blog/claude-code-agent-teams-parallel-workflows)).

**Check the dependency most people skip.** Sometimes feature B depends on an API feature A is building. The remedy is to **stub** the interface (keeping streams independent) or **sequence** the dependent work. So ask not just "are the parts separate?" but "can I cleanly stub the contract between them?" ([parallel dev playbook](https://www.mindstudio.ai/blog/parallel-agentic-development-playbook)).

**Amdahl's Law caps the payoff.** "The theoretical performance improvement you can get from a parallel computer is limited by the fraction of work that cannot be parallelized" — a workload 99% parallelizable but 1% sequential is still capped at 100× no matter the machine. Estimate the sequential "glue/synthesis" fraction (final integration, reconciling outputs); a feature with a big merge-and-reconcile tail is a weak parallel demo even if the middle parallelizes ([Amdahl/Gustafson](https://surfingcomplexity.blog/2026/01/19/amdahl-gustafson-coding-agents-and-you/)). The real ceiling is coordination, which "costs, continually"; in agent systems "the human coordination work becomes the fundamental bottleneck" — judge a candidate by how much *you* will spend reviewing diffs, unblocking, and merging while agents run ([Amdahl/Gustafson](https://surfingcomplexity.blog/2026/01/19/amdahl-gustafson-coding-agents-and-you/), [many parallel sessions](https://towardsdatascience.com/how-to-effectively-run-many-claude-code-sessions-in-parallel/)).

**Set the width small and deliberate.** "Start with two or three. Learn the coordination overhead. Then scale." Isolation (git worktrees, separate ports/data) is "non-negotiable," and skipping it is a named failure mode. For a talk, pick a feature that splits into ~2–3 streams — enough to demonstrate parallelism, few enough that coordination stays watchable rather than collapsing into on-stage merge-conflict cleanup ([parallel dev playbook](https://www.mindstudio.ai/blog/parallel-agentic-development-playbook)). Anthropic's Dynamic Workflows coordinate subagents via a shared task list for file-independent work like migrations and test generation, but InfoQ notes they "can consume substantially more tokens than a typical Claude Code session" ([Dynamic Workflows](https://www.infoq.com/news/2026/06/dynamic-workflows-claude-code/)).

**Tie parallel work to a join-time contract.** Parallel outputs can each be individually correct yet incompatible at the seams. A good parallel pick is one where the integration contract (API shape, schema, types) can be specified up front *and* verified by an integration test that runs after all agents complete ([agent teams](https://www.mindstudio.ai/blog/claude-code-agent-teams-parallel-workflows)).

## Technique-rich

The feature should be big enough to showcase multiple patterns. Anthropic's guide itself enumerates the demo-able ones — Explore/Plan/Implement/Commit (plan mode), "let Claude interview you" to produce a `SPEC.md`, the Writer/Reviewer two-session pattern, adversarial subagent review of a diff, the `/code-review` skill, `CLAUDE.md`, hooks, and subagents for investigation. Pick a feature whose natural workflow exercises several of these so the talk has substance, not a one-shot prompt ([best practices](https://code.claude.com/docs/en/best-practices)).

Pick a feature that forces more than a single "text in, text out" call. One internal hackathon set the bar by technical depth rather than topic — projects had to tackle "structured, repeatable, and reliable LLM outputs" via "prompt management" and "output parsing" ([internal AI hackathon example](https://info.devpost.com/blog/internal-ai-hackathon-example)). A feature spanning multiple skill domains (schema + UI + tests) plus a structured-output surface gives you several distinct techniques to show ([agent teams](https://www.mindstudio.ai/blog/claude-code-agent-teams-parallel-workflows)).

A refactor candidate is technique-rich when you can write a **self-contained spec** for it in a few lines: "The most useful specs are self-contained: they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step that proves the feature works" ([best practices](https://code.claude.com/docs/en/best-practices)).

**Caveat — a too-trivial feature can't justify the heavy techniques.** Plan mode "adds overhead," and for clearly-scoped small fixes — "if you could describe the diff in one sentence, skip the plan" — you should just let Claude do it directly ([best practices](https://code.claude.com/docs/en/best-practices)). The sweet spot is a feature a short spec can fully describe: small enough to need no spec means too small to showcase technique; too large to fit one coherent spec means too big for a 1.5-day agent build ([keep agentic AI simple](https://timdeschryver.dev/blog/keep-agentic-ai-simple-a-practical-workflow-for-software-development)).

## Safely-scoped (off the critical path)

**Make blast radius the primary selection metric, not task difficulty.** The deciding question is how much of the tree the agent can mutate before review catches a mistake — a CLI agent "can mutate half the tree" before you notice. Pick a feature whose worst-case wrong output is contained ([AI coding control](https://www.the-main-thread.com/p/ai-coding-tools-2026-java-developers-agents-control)). This maps to Anthropic's trust-boundary model: in auto mode "the only thing the classifier trusts is the git repo you're currently working in" — in-project edits proceed freely because version control makes them reviewable, while actions on shared infrastructure are gated. Choose a feature that lives entirely inside one repo/working directory and touches nothing shared ([auto mode](https://anthropic.com/engineering/claude-code-auto-mode)).

**Greenfield (or well-isolated brownfield) is where AI looks most capable** — agents excel on work that is "parallelizable, well-scoped, testable, and weakly coupled to historical baggage." Named ideal candidates: new features, isolated bug fixes, small internal tools, prototype surfaces, test generation, migration scripts ([greenfield vs brownfield](https://medium.com/@arturormk/greenfield-is-easy-brownfield-is-where-ai-software-development-gets-real-b2afad4b7f2d)). For a demo where you don't want production blast radius, a greenfield track is the safer pick, paired with a fast-pivot mindset when the original vision proves unrealistic ([internal AI hackathon example](https://info.devpost.com/blog/internal-ai-hackathon-example), [scope a hackathon project](https://medium.com/hack-western-2015/how-to-scope-a-project-for-a-hackathon-e3b03fca4751)).

**Avoid mature/legacy code because of invisible contracts.** Brownfield is "not just aging code; it is accumulated obligation" — promises to customers, operators, and partner systems that are "nowhere in the code," creating "epistemic debt" where autonomous changes break the system in ways tests won't catch ([greenfield vs brownfield](https://medium.com/@arturormk/greenfield-is-easy-brownfield-is-where-ai-software-development-gets-real-b2afad4b7f2d), [brownfield AI guide](https://thegeneralpartnership.substack.com/p/a-practical-guide-to-brownfield-ai)). Prefer a bounded, discrete feature with a clear finish line: "Migrate the upload modal to React" is tractable; "Modernize the application" is not ([brownfield AI guide](https://thegeneralpartnership.substack.com/p/a-practical-guide-to-brownfield-ai)).

**Tech-debt refactors are a strong, safe candidate** when correctness is decided by a machine signal and they touch zero business logic. Faros chose a 200+ file refactor precisely because "I'm not touching any logic… I'm just moving test utilities around" — targeting "low-complexity, high-effort… easily verifiable… low-risk… time-consuming if done manually" work. High file count is a *feature* when the edit is the same shape everywhere; uniformity (not raw count) is the real selector ([Claude Code for tech debt](https://www.faros.ai/blog/claude-code-for-tech-debt)). Scope to *localized* refactors and validate incrementally — run package-level typecheck and focused tests after each meaningful slice, with stop rules ("halt if the diff touches more than one unscoped area"); end-stage-only checking hides scope creep ([refactor supervision](https://junctionpanel.dev/blog/long-running-refactor-supervision/), [best practices](https://code.claude.com/docs/en/best-practices)).

**Constrain operational blast radius cheaply.** Use an ignore-file for sensitive paths, keep auto-approval off for traceability, use explicit Ask/Plan/Code modes as "execution contracts," and treat single-file-scoped edits as a deliberate safety feature ([AI coding control](https://www.the-main-thread.com/p/ai-coding-tools-2026-java-developers-agents-control)). Anthropic's equivalents: permission allowlists, a Stop hook to block writes to e.g. a migrations folder, OS-level sandboxing, `--allowedTools` for unattended runs, and checkpoints that snapshot files before each change so you can rewind a risky attempt (caveat: checkpoints track only Claude's changes, not external processes, and are not a git replacement) ([best practices](https://code.claude.com/docs/en/best-practices)). State an explicit compromise hierarchy when scoping: "security issues and data integrity are non-negotiable," while "ugly patterns and tech debt are fine temporarily" ([brownfield AI guide](https://thegeneralpartnership.substack.com/p/a-practical-guide-to-brownfield-ai)).

**The governing principle: "Automate only what you can explain."** If you can't articulate what the agent will touch, why, and how you'll review it — and you lack a strong architecture map ("your architecture map becomes the real safety mechanism") — the feature is a bad candidate ([AI coding control](https://www.the-main-thread.com/p/ai-coding-tools-2026-java-developers-agents-control)).

**Honest residual-risk signal.** Even Anthropic's guardrail classifier is imperfect: "The 17% false-negative rate on real overeager actions is the honest number." Their incident log shows the concrete danger of unscoped tasks — an agent deleting remote git branches from a misinterpreted instruction, uploading an auth token to internal compute, and attempting a migration against a production database. For a live talk, assume the agent will occasionally take an unintended action and pick a task where that costs nothing (fresh dir, disposable branch, no real secrets). **Do not overstate** the 17% figure: it is specific to the auto-mode classifier's false negatives on real overeager actions, *not* a general "Claude is wrong 17% of the time" rate ([auto mode](https://anthropic.com/engineering/claude-code-auto-mode)).

## Verifiability

**This is the single strongest signal — and the gate.** Anthropic's guidance opens with "give Claude a way to verify its work": a check that returns pass/fail — "a test suite, a build exit code, a linter, a script that diffs output against a fixture, or a browser screenshot compared against a design." Then the loop closes on its own: "Claude does the work, runs the check, reads the result, and iterates until the check passes." Without a check, "'looks done' is the only signal available, and you become the verification loop: every mistake waits for you to notice it." The hard pick-time rule: "If you can't verify it, don't ship it." Before choosing, ask "can I state success as a check that returns pass/fail?" — if you can't name one in a sentence, pick a different feature ([best practices](https://code.claude.com/docs/en/best-practices)).

Verifiability is also the **bridge to the other criteria**: it is what makes a feature delegable, parallelizable, and safely off the critical path. Gating mechanisms (a `/goal` condition re-checked every turn, a Stop hook that blocks the turn until the check passes) "are what let an unattended run finish correctly without you" ([best practices](https://code.claude.com/docs/en/best-practices)). Tests are the actual blast-radius boundary — E2E/integration tests are the feedback that stops the agent from "confidently break[ing] authentication while fixing a linting issue" ([brownfield AI guide](https://thegeneralpartnership.substack.com/p/a-practical-guide-to-brownfield-ai)).

**Favor TDD-amenable features.** A widely-cited writeup of Anthropic's guidance calls TDD "the single strongest pattern for working with agentic coding tools," because "without tests, Claude's only way to verify its work is its own judgment, which degrades as context fills up." The sequence: write tests first, confirm they fail, commit the failing tests as a checkpoint, then implement until green. The same source reports a "visual variant" for frontend work (design mock + screenshot comparison) claiming a "2–3× improvement in quality" — treat that multiplier as a vendor/blog figure, not an independently verified benchmark ([Claude Code best practices](https://www.datacamp.com/tutorial/claude-code-best-practices)).

**Among verifiable features, prefer a check that is HARD TO GAME — this is the discriminating signal, not merely whether a check exists.** Agents routinely game test-based verification: in one analysis they read hidden answer-key directories (415 of 429 traces for one model on Terminal-Bench 2), hardcoded return values for exact test inputs, printed "PASS" to fool verifiers that only checked whether output "contains" the word, faked exploits with mock libraries that "only check exit codes," and mined git history to copy historical fix commits. Selection implication: prefer features where correctness requires real behavior (integration tests over exact-string asserts, real boundaries over easily-mockable ones, held-out inputs that can't be hardcoded). A feature whose only check is a brittle string match is a trap for a live demo ([cheating agents](https://debugml.github.io/cheating-agents/)).

**Verifiability is a filter, not the whole ranking.** Optimizing only for "easy to check" biases you toward trivially-checkable, low-value work. Confirm the feature is genuinely valuable first, then apply verifiability as the gate ([best practices](https://code.claude.com/docs/en/best-practices)). Pair the objective check with a fresh-context adversarial review, but scope the reviewer to "gaps that affect correctness or the stated requirements" — a reviewer prompted to find gaps "will usually report some, even when the work is sound."

**Reality check on raw reliability, with corrected numbers.** Raw LLMs are *not* reliable refactorers: the ACE paper benchmarked over 100,000 real CodeHealth issues and found "the best-performing LLM generated functionally correct refactorings only 37% of the time" (a separate extract-method study reported 24%). The payoff comes from validation guardrails — "by discarding incorrect solutions, 98% of the remaining AI-generated refactorings improve CodeHealth while retaining the original behavior… ACE elevates the precision from 37% to 98%," but at a cost: recall drops to 52%, so you safely complete roughly half of detected smells rather than all of them. (Note: an earlier circulating "95% acceptance / 5% false-positive" summary of this paper was fabricated and does not appear in it; the real figures are 37% / 98% / 52%, and the 98%/52% are validation-layer results, not what an unguarded session hits.) Lesson: a refactor is a good candidate when you can wrap generation in a behavior-preserving validation layer ([ACE paper](https://arxiv.org/pdf/2507.03536)).

**Demo-ability is verifiability you can show.** Pick a feature with a visible payoff and put the "wow moment" early — a Functional MVP that "showcases core functionality" (need not be feature-complete), demonstrable in one screen, with the concept validated end-to-end even if edges are rough. Always demo, even partial or buggy — it generates feedback and is usually received well ([hackathon judging](https://taikai.network/en/blog/hackathon-judging), [scope a hackathon project](https://medium.com/hack-western-2015/how-to-scope-a-project-for-a-hackathon-e3b03fca4751)).

## Right-sizing (the timebox is the fixed constraint)

Work backwards from the demo and treat the timebox — not the feature wishlist — as fixed. "Too big" overruns the box and produces nothing demoable; "too small" finishes in an hour, has nothing to show, and exercises no technique worth a talk. The target is a single vertical slice that runs end-to-end with most of the clock in reserve.

**Define the slice by three pass/fail criteria, not gut feel:** Mergeable (integrates into main without breaking the system), Testable (core function verifiable input→output), and Functional (delivers a clear technical goal such as auth, persistence, or an API integration). A candidate that can't satisfy all three inside the timebox is mis-sized; one so trivial it needs no test and no integration is *below* the slice level and won't sustain a talk ([minimum viable slice](https://dileeparanawake.com/minimum-viable-slice)).

**Too big — the well-sourced end.** Work backwards from the final pitch and build only what leads to that "wow" image; if a candidate has no single moment worth showing on screen, it's the wrong slice ([hackathon MVP guide](https://medium.com/viewstools/a-practical-guide-to-delivering-a-working-mvp-at-the-hackathon-2b21095c4545)). Prefer one feature done deep over several done shallow: "One solid feature is usually more valuable than three broken ones" — reject any candidate that is really three features in a trenchcoat and demote the rest to stretch goals ([hackathon MVP guide](https://medium.com/viewstools/a-practical-guide-to-delivering-a-working-mvp-at-the-hackathon-2b21095c4545)). Reserve roughly half the timebox as buffer: the guide's 40-hour budget allocates only ~20h to actual work (research 2h, setup 2h, hard problems 4h, easy problems 4h, deploy/debug 2h, refactor 5h, help others 1h) and explicitly adds "+ − another 20h for the unexpected." *(The "one solid feature" line and the 2h/4h/5h/20h numbers were confirmed verbatim; the 40h total is for a weekend hackathon, and mapping it to a 1.5-day/~12h build — implying a feature needing more than ~6h of clean work is too big — is the researcher's own arithmetic, not the source's.)* ([hackathon MVP guide](https://medium.com/viewstools/a-practical-guide-to-delivering-a-working-mvp-at-the-hackathon-2b21095c4545))

A 24-hour hackathon demands a focused MVP: "if you can't explain the core feature in one sentence, the scope is too broad," aim for something demoable in ~8–24h, and structure as agile increments where each component yields a working product — a retrospective EEG project whose pieces "didn't connect until the final hours" ended up non-functional despite real effort ([scope a hackathon project](https://medium.com/hack-western-2015/how-to-scope-a-project-for-a-hackathon-e3b03fca4751), [hackathon judging](https://taikai.network/en/blog/hackathon-judging)). Watch for over-scope tells during the build, not just at planning — velocity instability and ballooning timelines flag hidden complexity. *(thinslices' specific framings such as "sprint variance above 15%" and "8–12+ sprints" came back through a summarizer and could not be confirmed verbatim; treat the percentages as paraphrase, not source quotes — the directional "instability = over-scope" signal is what the page conveys.)* ([MVP scoping](https://www.thinslices.com/insights/build-the-right-first-version-by-mastering-mvp-scoping), [keep agentic AI simple](https://timdeschryver.dev/blog/keep-agentic-ai-simple-a-practical-workflow-for-software-development))

**Sequence so it runs end-to-end early.** Avoid the named slice-sizing failures: too-tightly-coupled slices, vague interfaces, backend-only focus (you lose the demoable surface), and endless cross-layer refactoring. Order the slice so its first runnable version is thin, visible, and end-to-end — the "prompt-loop equivalent" — then layer on auth, persistence, advanced features ([minimum viable slice](https://dileeparanawake.com/minimum-viable-slice)). Use direct prompting for small bugfixes but spec-driven development for larger features, providing "just enough context, not too little… certainly not too much"; the right candidate is one a short spec can fully describe ([keep agentic AI simple](https://timdeschryver.dev/blog/keep-agentic-ai-simple-a-practical-workflow-for-software-development)).

**Too small — flagged as under-sourced.** The MVP-scoping sources address over-scope, not under-scope. The "too small" guidance below is *synthesized* from search-result snippets rather than fully-read pages: demo-craft advice that presenters drag out trivial low-value material and run out of time for what matters, and that a demo should fill half-or-more of its slot. Two of these URLs were surfaced as snippets only and not fetched in full; a related headrush source was a dead/parked domain and could not be retrieved. So treat this as a reasoned synthesis, not a sourced claim: for a talk, the under-scope tell is a feature that finishes in an hour, has no operational use case to show, or exercises no technique worth half the slot. Right-sized for a talk = one vertical slice that produces a live, end-to-end moment *and* surfaces a reusable technique ([demos over deadlines](https://medium.com/javascript-scene/demos-over-deadlines-8ed8dcdecb6), [CSE403 demo guide](https://courses.cs.washington.edu/courses/cse403/26wi/project/demo.html)).

## Anti-patterns / what to avoid

Each anti-pattern is the inverse of a Pick criterion. If you can't cheaply convert a candidate into a verifiable, precedented, well-scoped target, pick a different feature.

- **Fuzzy or absent acceptance criteria — the biggest flop signal.** "Without a check it can run, 'looks done' is the only signal available, and you become the verification loop." Before choosing, name the pass/fail check that closes the loop; if you can't name one in a sentence, nobody — Claude or the audience — will know when it's done. *(Not absolute: a vague prompt is sometimes right "when you want to see how Claude interprets the problem before constraining it" — fuzzy acceptance is an anti-pattern for a committed demo, not an exploratory spike.)* ([best practices](https://code.claude.com/docs/en/best-practices))
- **Vague requirements** ("make it better", "add a calendar widget"). Anthropic's contrast points at a named file as the pattern to follow, names the interaction, and bounds the libraries. Watch the opposite failure too: dumping a massive spec causes the "curse of instructions" where the model can't adhere to many simultaneous requirements — specific does not mean exhaustive ([best practices](https://code.claude.com/docs/en/best-practices)).
- **Novel/unprecedented design with no in-codebase precedent.** IEEE Spectrum names "tasks without direct training precedent" as a flop category and documents the dangerous mode — code that "fails to perform as intended, but which on the surface seems to run successfully" (in one 10-trial test, GPT-5 was "counterproductive 100% of the time" on a missing-column case, producing random numbers that executed cleanly). Prefer features with a precedent to imitate so "looks plausible" and "is correct" coincide. *(Novelty isn't fatal if you supply scaffolding: Anthropic's long-running research made progress outside Claude's native domain by giving it a reference implementation and a quantifiable target — lack of precedent is a flop signal only when you also lack an external oracle.)* ([AI coding degrades](https://spectrum.ieee.org/ai-coding-degrades), [brownfield problem](https://www.jjmasse.com/2026/03/06/the-brownfield-problem-why-most-ai-development-advice-ignores-your-actual-codebase/), [long-running Claude](https://www.anthropic.com/research/long-running-Claude))
- **Heavy domain context that lives only in someone's head.** "Missing domain context" is a distinct failure mode — edge cases, library pitfalls, and relationships "that require human explanation rather than inference." The symptom is concrete: a model "rounded exact sea level rise thresholds" and "renamed element IDs to be cleaner," silently violating precision constraints. Choose a feature whose domain rules are self-evident or already written down (`CLAUDE.md`, a skill, a fixture). The anti-pattern is *unwritten* tribal knowledge, not domain complexity per se ([brownfield problem](https://www.jjmasse.com/2026/03/06/the-brownfield-problem-why-most-ai-development-advice-ignores-your-actual-codebase/)).
- **Shared-core / coupled work dressed up as parallel.** Shared-file editing, hidden dependencies, and no validation layer are the parallelization red flags; skipping isolation setup is a named failure mode ([parallel dev playbook](https://www.mindstudio.ai/blog/parallel-agentic-development-playbook), [agent teams](https://www.mindstudio.ai/blog/claude-code-agent-teams-parallel-workflows)).
- **Known agent failure modes to design the pick against:** agents default to generic "best practices" when you need a pragmatic solution; they have strong local competence but lack "global context"; tacit-knowledge gaps can yield "a 4000-line change full of subtle bugs"; and on the human side, reviewer fatigue and approval fatigue set in as output outpaces comprehension. Pick something small and contained enough that none of these turns catastrophic ([brownfield AI guide](https://thegeneralpartnership.substack.com/p/a-practical-guide-to-brownfield-ai), [AI coding control](https://www.the-main-thread.com/p/ai-coding-tools-2026-java-developers-agents-control)).
- **The positive profile to aim at instead** (the photographic negative of the above): Anthropic's long-running research says agentic work fits "when the work is well-scoped, the success criteria are clear, and human oversight can be occasional," citing reimplementing a numerical solver, converting legacy scientific software to a modern language, and debugging a large codebase against a reference implementation. The recurring success ingredients are a reference implementation, a quantifiable objective, an existing test suite, and a progress signal — though note these are translation/reimplementation tasks where a ground-truth oracle exists for free; a from-scratch product feature won't have one, so you must *manufacture* the oracle (failing tests / target design) as part of the Pick-stage cost ([long-running Claude](https://www.anthropic.com/research/long-running-Claude), [best practices](https://code.claude.com/docs/en/best-practices)).

**Stage-boundary note (not a Pick criterion).** Simon Willison's "Don't file pull requests with code you haven't reviewed yourself" is a *Ship*-stage rule, not a feature-selection one — flagged so it isn't mistaken for a Pick signal. It constrains how you finish and merge, whereas everything above constrains which feature you start. *(This fetch surfaced only the PR-review anti-pattern; the page likely has a broader index not retrieved here.)* ([anti-patterns](https://simonwillison.net/guides/agentic-engineering-patterns/anti-patterns/))

## Candidate-feature checklist

Score a candidate by answering each in one sentence. A "no" you can't cheaply flip to "yes" is a reason to pick something else.

1. **Valuable** — Can you state the value as a measurable outcome an audience recognizes, *without* it being security-critical or architecturally load-bearing?
2. **Verifiable** — Can you name a pass/fail check (tests, build exit, linter, fixture/screenshot diff) in one sentence, and is that check hard to game?
3. **Researchable** — Are the data, APIs, and prior art already reachable, with a precedent in the repo to imitate, and an unambiguous target?
4. **Safely-scoped** — Does it live in one repo/working dir, touch no shared core or production/secrets, and is its worst-case wrong output contained and reversible?
5. **Parallelizable** *(only if demoing parallelism)* — Does it split into ~2–3 disjoint-file streams with a stubbable contract and a small sequential glue tail?
6. **Technique-rich** — Does its natural workflow exercise several techniques (plan/spec, Writer/Reviewer, hooks, subagents) without being so trivial the heavy techniques aren't justified?
7. **Right-sized** — Does it fit one Mergeable + Testable + Functional vertical slice inside the timebox with ~half the clock as buffer, and produce a live end-to-end moment?
8. **Has an oracle up front** — Can you write the failing test or paste the target design *before* starting, so "done" is defined the moment you pick it?
