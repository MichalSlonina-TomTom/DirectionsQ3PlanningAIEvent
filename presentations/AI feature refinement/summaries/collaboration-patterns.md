# Collaboration patterns — multiple people on one refinement/build

How a team can refine and build a single feature together with Claude. This is the speaker's
synthesis/framing, now grounded against first-party docs and practitioner write-ups, with extra
patterns pulled from the research. Cross-refs: [`key-findings.md`](key-findings.md),
[`candidate-techniques.md`](candidate-techniques.md), and the marketplace scan
[`../research/tomtom-marketplace-skills.md`](../research/tomtom-marketplace-skills.md).

**Mental model:** Claude Code sessions are single-player, but collaboration happens through shared,
durable artifacts — **git and plan files — not through a shared chat.** "Collaborating with Claude"
really means coordinating several humans (each with their own Claude) around common context.

## A. Several *humans* collaborating on one feature

1. **The plan/spec file is the team's shared brain.** Agree on a `SPEC.md` / plan file together up front, commit it, everyone's Claude reads the same one. Highest-leverage coordination move — keeps three people's Claudes from drifting in three directions. **[supported]** Anthropic's flow is to interview-then-["write a complete spec to SPEC.md"](https://code.claude.com/docs/en/best-practices) and execute it from a fresh session; [Spec Kit](https://github.com/github/spec-kit) formalizes the same idea with version-controlled specs that "become executable." *Honest caveat:* the strongest first-party "check it into git so your team can contribute… compounds in value" quote is about [`CLAUDE.md` conventions](https://code.claude.com/docs/en/best-practices), not the per-feature spec; the spec docs frame it as cross-session reuse for one dev, not explicitly whole-team. And a committed spec is advisory ([delivered as a user message, "no guarantee of strict compliance"](https://code.claude.com/docs/en/memory)) and can mislead if it goes stale — so it *reduces* drift, doesn't *enforce* alignment.
2. **Commit shared `.claude/` config.** A committed `CLAUDE.md` plus shared slash commands, subagents, and hooks means the whole team's Claude behaves consistently. Keep `CLAUDE.md` short — a bloated one gets ignored. **[supported]** All four config types are committable team-shared config: [`CLAUDE.md` is "shared with your team through version control"](https://code.claude.com/docs/en/memory) (target ["under 200 lines… longer files reduce adherence"](https://code.claude.com/docs/en/memory)); [`.claude/commands/*.md` or `.claude/skills/<name>/SKILL.md`](https://code.claude.com/docs/en/skills) ("Commit `.claude/skills/` to version control"); and project [`.claude/settings.json` hooks](https://code.claude.com/docs/en/hooks-guide) ("can be committed to the repo"). *Caveat — soften "consistently":* only hooks are deterministically enforced; [`CLAUDE.md`, commands and subagents "shape behavior but are not a hard enforcement layer"](https://code.claude.com/docs/en/memory). For a rule that must always fire, write a hook.
3. **Split into parallelizable vertical slices, one owner each.** This is the "parallelizable" criterion from the Pick phase — and the highest-leverage version of it is mapping file ownership *before* launching: [agent-teams' top rule is "break the work so each teammate owns a different set of files,"](https://code.claude.com/docs/en/agent-teams) [Spec Kit emits `[P]` parallel-task markers](https://github.com/github/spec-kit), and [worktrees isolate the file edits](https://code.claude.com/docs/en/worktrees). **[partially supported]** The slice-with-one-owner half is strong; the "integration point is the PR queue, *not* a live session" framing is the speaker's synthesis and partly cuts against the evidence — Anthropic's [agent teams *are* a documented live-coordination model](https://code.claude.com/docs/en/agent-teams) (file-locked shared task list, teammates messaging directly), and the PR-queue framing is a [third-party practitioner pattern](https://www.mindstudio.ai/blog/parallel-agentic-development-claude-code-worktrees), not Anthropic doctrine. Treat it as *choose by coordination need*, not either/or. *Premise caveat:* Anthropic warns ["most coding tasks involve fewer truly parallelizable tasks than research"](https://www.anthropic.com/engineering/built-multi-agent-research-system) and multi-agent burns ~15× the tokens — many features don't decompose cleanly.
4. **Pair / mob *on the plan*, solo on the build.** Group-driving the decisions (Pick → Research → Plan) pays off; group-driving the typing is slow. **[partially supported — and the "solo build" half is contradicted]** Collaborating on planning is sound: planning is the [judgment-heavy phase engineers keep](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic), and mob-with-AI teams explicitly mob the spec together. But "fan out to individuals for Build" is **flagged**: the most on-point evidence rejects it — a [team that tried splitting solo for the Build found "reintegration was painful… we're faster together"](https://blog.crisp.se/2025/06/02/michaelgothe/mob-programming-with-ai-inside-a-high-performing-teams-journey), and [Atlassian's mob keeps the mob together through development, testing and retro](https://www.atlassian.com/blog/atlassian-engineering/mobbing-with-ai). The fan-out support elsewhere is *agent* orchestration (parallel AI workers), not humans dividing the Build. So: mob the plan; treat "fan out humans for Build" as a contestable choice with documented downside, defensible only for cleanly-decomposable, independently-verifiable slices.
5. **Review and integrate with Claude in a fresh context.** Each PR reviewed by an independent context (author shouldn't grade their own work). Tools: `multi-agent-code-review`, `make-pr-green` (PR #24). **[strongly supported]** ["A fresh context improves code review since Claude won't be biased toward code it just wrote"](https://code.claude.com/docs/en/best-practices) — Anthropic prescribes a Writer/Reviewer two-session split and an adversarial review subagent that "sees only the diff and criteria"; practitioner TDD guidance echoes ["one Claude write tests, then another write code to pass them."](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/guide/workflows/tdd-with-claude.md) *Caveat:* the guidance covers the review/grading step, not the "integrate each PR" action; and ["a reviewer prompted to find gaps will usually report some, even when the work is sound"](https://code.claude.com/docs/en/best-practices) — scope it to correctness and stated-requirement gaps, not style, to avoid over-engineering.
6. **Hand off cleanly across people/sessions.** Context travels via durable, shared artifacts — git commits, PR descriptions, tracker comments, handoff docs — not an ephemeral chat. Tools: `wip`/`wip-save`, `jira-handover`/`jira-resume` (PR #18). **[supported]** Creating the PR with the [`gh` CLI auto-links the session for `claude --from-pr`](https://code.claude.com/docs/en/best-practices), and the [SPEC.md flow carries the plan across the session boundary](https://code.claude.com/docs/en/best-practices); community [`/handoff:create` → `HANDOFF.md` → `/handoff:resume`](https://github.com/ykdojo/claude-code-tips/blob/main/skills/handoff/SKILL.md) and [JIRA handover skills](https://github.com/grandcamel/jira-assistant-skills) populate the category. *Two wording caveats:* "only committed artifacts" is too narrow — cross-machine handoff often rides a tracker comment (durable/shared but not committed), and same-machine resume works via uncommitted filesystem state; and `wip`/`jira-handover` are the talk's own labels for that category, not citable Anthropic products.

## B. One *human* orchestrating several *Claude agents*

- **Use git worktrees, not a swarm in one session** — each parallel task gets its own [isolated working copy on its own branch (`claude --worktree <name>`)](https://code.claude.com/docs/en/worktrees); the human integrates the branches. **[supported]** A [26-agent design "ran out of context in less than 15–20 minutes"](https://medium.com/@ilyas.ibrahim/how-i-made-claude-code-agents-coordinate-100-and-solved-context-amnesia-5938890ea825), and worktrees let one human "build a feature in one terminal while fixing a bug in a second." *Caveat — not strictly either/or:* worktrees isolate *file edits* while [subagents/agent-teams coordinate the *work*, and can be combined via `isolation: worktree`](https://code.claude.com/docs/en/worktrees); and the anti-swarm evidence is Build-specific — [for breadth-first Research a swarm actually wins (90.2% on Anthropic's eval)](https://www.anthropic.com/engineering/built-multi-agent-research-system).
- **Honest caveat:** multi-agent is a poor fit for most *coding* — great for research, but [burns ~15× tokens and agents lose track of each other's work](https://www.anthropic.com/engineering/built-multi-agent-research-system). Fan out agents for research/blast-radius; for the build, prefer worktree isolation + one human integrator. **[supported]** The descriptive thesis is airtight first-party Anthropic evidence; the "+human integrator" remedy is synthesis from the documented [worktree guidance](https://code.claude.com/docs/en/worktrees). *Boundary is moving:* Claude Code's [Dynamic Workflows now apply multi-agent orchestration to large-scale coding](https://www.infoq.com/news/2026/06/dynamic-workflows-claude-code/) (widespread-bug investigation, large migrations, security audits) — exactly the high-value, parallelizable exception the caveat predicts.

## More patterns from the research

Genuinely new patterns not already covered above, deduplicated against the existing list and each other.

**Coordinating humans-with-humans (mostly Plan / Verify / Share):**

- **Spec-review meeting as the alignment gate** — the whole team reviews the ~200-line spec *before* anyone codes; far faster and more objective than reviewing 2,000 lines later, and surfaces reuse ("that validation already exists"). *Plan; humans-with-humans.* Caveat: a rushed spec gives false confidence. [MS Learn](https://learn.microsoft.com/en-us/training/modules/spec-driven-development-github-spec-kit-enterprise-developers/10-scale-spec-driven-development-team-collaboration), [Uramanovich](https://medium.com/@uramanovich/spec-driven-development-the-key-to-aligning-team-and-improving-code-quality-a27db0b06dd8)
- **Team constitution as conflict arbiter** — a version-controlled `constitution.md` of project-wide principles (REST/security/perf budgets) that decides technical disagreements ("the spec requires X" vs "I'd do it differently"). *Plan; humans-with-humans.* Caveat: not auto-enforced for AI-generated code. [MS Learn](https://learn.microsoft.com/en-us/training/modules/spec-driven-development-github-spec-kit-enterprise-developers/10-scale-spec-driven-development-team-collaboration), [Augment](https://www.augmentcode.com/guides/claude-code-spec-driven-development)
- **45-minute coupling review before parallel work** — after decomposition, a short synchronous meeting to find hidden couplings static analysis can't ("four engineers in a room can spot couplings no tool catches"), front-loading conflict detection into Plan. *Research/Plan; humans-with-humans.* Caveat: doesn't scale past a small co-available team. [Josh McDonald](https://joshmcdonald.medium.com/running-a-small-team-on-a-big-project-spec-driven-development-with-claude-code-9a1b97f58551)
- **`specs/INDEX.md` as the live project board** — one markdown table tracking every feature's spec status / owner / in-flight / blocked, plus per-task ownership tags, as the async single source of truth across time zones. *Plan; both.* Caveat: shared markdown has no locking — concurrent writes silently overwrite. [Josh McDonald](https://joshmcdonald.medium.com/running-a-small-team-on-a-big-project-spec-driven-development-with-claude-code-9a1b97f58551), [Augment](https://www.augmentcode.com/guides/claude-code-spec-driven-development)
- **CLAUDE.md changes as code review + CI compliance gate** — treat edits to shared config as reviewed code (team discussion before merge), backed by a CI validator that blocks PRs diverging from documented standards; calibrate by team size (2–5 share one file; 15+ assign dedicated roles). *Share; both.* Caveat: a single practitioner's template (custom scripts, role titles), not vendor-documented. [SmartScope](https://smartscope.blog/en/generative-ai/claude/claude-code-creator-team-workflow-best-practices/)
- **Specs as the onboarding artifact** — new members get a reading list (constitution + key specs + ADRs) and start on small scoped tasks from `tasks.md`; resolved conflicts are documented in the spec so debates aren't re-litigated. *Share; humans-with-humans.* Caveat: only works if specs are kept living — drifted specs onboard a fiction. [MS Learn](https://learn.microsoft.com/en-us/training/modules/spec-driven-development-github-spec-kit-enterprise-developers/10-scale-spec-driven-development-team-collaboration)
- **Dogfood-and-fast-feedback loop** — ship internally many times a day and make dogfooding the coordination mechanism (Anthropic: ~60–100 internal releases/day, ~5 PRs/dev/day). *Build/Verify/Share; humans-with-humans.* Caveat: one self-reporting AI-native team; needs a daily-release pipeline most orgs lack. [Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/how-claude-code-is-built)
- **Reviewer-becomes-bottleneck at scale** — when builders (or one dev running several agents) speed up, review becomes the constraint; adopting Claude Code without scaling review capacity moves the jam rather than removing it. *Verify; both.* Caveat: any specific reviewer-ratio figure is unverified secondary material; the bottleneck dynamic is the durable point. [Anthropic teams](https://claude.com/blog/how-anthropic-teams-use-claude-code)

**One human orchestrating agents (mostly Build / Verify):**

- **Lead + file-locked shared task list (agent teams)** — an experimental lead session spawns 3–5 teammates with their own context windows, a mailbox, and a shared task list whose claiming uses file locking; dependencies auto-unblock. *Build; human-orchestrating-agents.* Caveat: experimental/off-by-default, token cost scales linearly, status can lag, no resume for in-process teammates, same-file edits overwrite. [Agent teams](https://code.claude.com/docs/en/agent-teams)
- **Resource isolation per worktree** — beyond files, isolate runtime: distinct ports, per-worktree `node_modules` (not symlinked), copied (not symlinked) `.env`, serialized DB migrations, and a `.worktreeinclude` to copy gitignored config in. *Build; human-orchestrating-agents.* Caveat: practical attention ceiling is low (~2–3 sessions before monitoring breaks down); parallelism is bounded by the human's review capacity. [MindStudio](https://www.mindstudio.ai/blog/parallel-agentic-development-git-worktrees), [Dan Does Code](https://www.dandoescode.com/blog/parallel-vibe-coding-with-git-worktrees)
- **Plan-approval gate before any agent writes code** — teammates work in read-only plan mode until the lead approves the approach (steered by criteria like "reject plans that modify the schema"); catches architectural/ownership collisions while they're cheap. *Plan; human-orchestrating-agents.* Caveat: a vague prompt adds latency without reliably catching overlaps. [Agent teams](https://code.claude.com/docs/en/agent-teams), [Addy Osmani](https://addyosmani.com/blog/code-agent-orchestra/)
- **Define shared contracts first, then merge in dependency order** — fix API shapes / interfaces / error formats in dedicated files up front, split by directory ownership, build each in its own worktree, then merge contracts → backend → frontend → tests with a final integration-validator pass. *Build; human-orchestrating-agents.* Caveat: worktrees isolate files, not external state — DBs, ports and `.env` still collide, and incompatible assumptions fail the merged system with zero file conflicts. [AakashX](https://www.aakashx.com/blog/parallel-claude-code-agents/), [Addy Osmani](https://addyosmani.com/blog/code-agent-orchestra/)
- **Verification quality-gate pyramid** — fastest-first hooks before human eyes (format → lint → typecheck → secret scan → unit tests → diff-size guard → fresh-context review subagent); a `TaskCompleted` hook runs lint+tests before a task can be marked done. *Verify; human-orchestrating-agents.* Caveat: silent failures — each local slice passes but the merged app fails — need an integrated validation pass. [dev.to](https://dev.to/javatarz/multi-agent-development-workflows-with-claude-code-n23), [Addy Osmani](https://addyosmani.com/blog/code-agent-orchestra/)
- **Compaction-survival hooks** — pre-compaction hook snapshots the handoff doc, post-compaction hook re-injects it, and a stop-gate blocks Claude from ending until it has written its summary/resume sections — making the eventual person-to-person handoff trustworthy. *Build; human-orchestrating-agents.* Caveat: the gate enforces that sections *exist*, not that they're accurate. [handoff plugin](https://github.com/thepushkarp/handoff)
- **Card/spec "factory" dispatch with reject-with-feedback** — a solo lead grooms cards (acceptance criteria + non-goals) before any code; workers atomically claim ready cards in their own worktrees, and rejected work reopens *with* feedback the next agent reads so failures aren't repeated. *Share; human-orchestrating-agents.* Caveat: workers don't inherit the lead's conversation, so handoffs lose nuance; this layer is Claude-locked. [dev.to](https://dev.to/javatarz/multi-agent-development-workflows-with-claude-code-n23), [Addy Osmani](https://addyosmani.com/blog/code-agent-orchestra/)

**Distribution, integration and review tooling (both):**

- **Plugins + private marketplace to distribute one governed setup** — bundle commands/subagents/hooks/MCP into a one-command install; host a `marketplace.json` so "team consistency becomes a commit," not per-person setup. *Share; both.* Caveat: public beta; installed ≠ enabled (members can disable). [Plugins blog](https://claude.com/blog/claude-code-plugins)
- **`@claude` in PRs/issues as the shared work-intake channel** — anyone mentions `@claude` on an issue/PR and Claude branches, implements, runs format/lint/test, and opens a reviewable PR in the open thread; split a general `claude.yml` from a read-only `claude-review.yml` and allowlist exact commands. *Build/Verify; both.* Caveat: read-write tokens are a real attack/cost surface — least privilege, secrets in GitHub Secrets, start read-only then widen. [GitHub Actions docs](https://code.claude.com/docs/en/github-actions), [Chamith](https://chamith.medium.com/how-we-integrated-claude-code-into-our-github-workflow-97a5db8bcb8e), [claude-code-action](https://github.com/anthropics/claude-code-action)
- **Multi-agent automated PR review (inline + one overview)** — on PR open, parallel agents each hunt a different bug class, a verification step cuts false positives, findings post as one overview comment plus inline lines; it *never* approves ("still a human call") and raised substantive-review coverage at Anthropic from 16% → 54%. *Verify; both.* Caveat: cost ~$15–25/review; value concentrates on large PRs (84% of 1000+-line PRs get findings vs 31% of small). [Code review blog](https://claude.com/blog/code-review)
- **AI-review false positives erode trust (the counterweight)** — independent audits attribute noise to exclusion-list ignorance (~40%), config misclassification (~30–42%), and fabricated evidence (~15%); a single false citation can sink trust in the whole tool. *Verify; human-orchestrating-agents.* Caveat: directly tensions Anthropic's <1%-incorrect figure (different setups, not strictly comparable) — present both. Fix with path-scoped filters, pre-flag verification, and exclusions placed where the model applies them. [bdigitalmedia](https://tech.bdigitalmedia.io/blog/diagnosing-ai-review-false-positives/), [Code review blog](https://claude.com/blog/code-review)
- **Spec-grounded review + integrator-proposes / human-executes-merge** — a `/spec-aware-review` diffs the implementation against the spec (catching code that's technically correct but does the wrong thing), and an integrator subagent reads all parallel diffs to propose a merge plan flagging conflicts the merge tool won't see — but "merging is a decision that needs a human." *Verify/Share; both.* Caveat: only as good as the spec; the integrator proposes, a person executes. [Josh McDonald](https://joshmcdonald.medium.com/running-a-small-team-on-a-big-project-spec-driven-development-with-claude-code-9a1b97f58551), [Augment](https://www.augmentcode.com/guides/claude-code-spec-driven-development)
- **Read-only cross-worktree conflict detection (`clash`)** — because worktrees *defer* conflicts to merge time, `clash` simulates three-way merges between worktree pairs (read-only, via `git merge-tree`) to surface which files *would* conflict before integration. *Verify; both.* Caveat: it detects but does not resolve, and nothing stops the overlap being created. [clash](https://github.com/clash-sh/clash)
- **Compare-and-choose: assign one task to multiple agents** — on Agent HQ, assign an issue to Claude/Codex/Copilot to compare how each reasons about tradeoffs before code review, surfacing edge cases early. *Plan; human-orchestrating-agents.* Caveat: this is one human orchestrating agents (not teammates), multiplies cost and review burden (three PRs per task), and only pays off on genuinely ambiguous work. [Agent HQ](https://github.blog/news-insights/company-news/pick-your-agent-use-claude-and-codex-on-agent-hq/)
- **Local-to-cloud delegation with context handoff** — plan with a local agent, then `/delegate` passes the full chat history to a cloud agent that runs on remote infra and opens a PR; the session even surfaces back in another teammate's editor. *Build; both.* Caveat: cloud agents can't see live editor context (failed tests, selections), so it must be packaged into the handoff or the agent works blind. [VS Code cloud agents](https://code.visualstudio.com/docs/copilot/agents/cloud-agents)

---

**One-liner for the deck:** *coordinate through artifacts (spec, git, PRs), parallelize the research, serialize the integration, and keep a human as the integrator.*
